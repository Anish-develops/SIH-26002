NER Sentinel - Prototype MVP Specification

Build-ready scope | What the team should ship for the prototype

SIH Problem Statement 26002 | MDoNER | Software | Transportation & Logistics

Prototype north star: predict disruption, keep essential deliveries moving, and make every decision explainable.

1. MVP objective

Ship a visually polished, integrated prototype that proves the product loop: observe -> assess risk -> recommend -> alert -> reroute -> report -> synchronize.

The single demo scenario

Use one synthetic corridor, a small set of road segments, 2-3 simulated vehicles, 3-5 deliveries, and several synthetic incidents. The exact places and numbers are configurable; do not present the seeded values as real-world measurements.

Scenario seed   ->   Road risk changes   ->   Incident confirmed   ->   Route recalculated   ->   Driver alerted   ->   Delivery impact shown

Visual system

Use a 12-column desktop grid and 4-column mobile grid. Keep map as the primary visual anchor.

Use one accent color for brand/interactive elements; reserve green/amber/red only for operational status.

Cards: 12-16 px radius, subtle borders, minimal shadows. Avoid glassmorphism or heavy gradients.

Typography: bold numeric KPIs, compact labels, sentence-case controls. Never make the screen feel like a spreadsheet.

DEMO / SYNTHETIC DATA badges must be visible but visually secondary.

All critical status has icon + text + color; never use color alone.

6. Synthetic data pack

Create the prototype around a reusable seed package rather than embedding values directly in UI code.

File / collection

Purpose

roads.geojson

Road geometry and static attributes for the demo region/corridor.

incidents.json

Synthetic incidents used for initial map state and scenario events.

vehicles.json

Starting positions, trip IDs and deterministic movement paths.

deliveries.json

Synthetic essential-goods deliveries with priorities and destinations.

weather.json

Synthetic/replayed weather observations matching the future weather adapter schema.

risk_baseline.json

Initial risk values and factor explanations for demo reproducibility.

scenarios.json

Named scenarios: normal, heavy rain, landslide, blocked road, recovery.

Seed ruleEvery file must include environment="demo" and source="synthetic" (or an explicit replay source). No real-time claim should be inferred from seeded data.

8. Prototype QA checklist

Web dashboard works at common laptop widths; mobile app works on a modern Android-sized viewport.

No layout shift when map, cards, or alert states change.

Every loading/error/empty state has deliberate UI.

Offline report remains visible after app restart until synced.

Driver receives a route change without losing current trip context.

Scenario reset returns map, vehicles, deliveries and alerts to the seeded baseline.

All risk outputs show source, timestamp, horizon, and prototype/model version.

No screen contains unexplained “AI” scores or fake government data claims.

9. Handover notes for the team

Keep domain logic independent from UI so real government adapters can be plugged in later.

Keep all external providers behind adapters: weather_provider, road_provider, disaster_provider, routing_provider.

Keep risk weights configurable and versioned.

Use stable IDs and idempotent event ingestion from day one.

Build the demo reset and scenario console early; it saves enormous time during judging rehearsals.
